# RideLens — for a prospective data partner

**Every ride. One comparison.** What each way of making a trip costs, and how
firm each number is.

Prepared 2026-09-25. Everything below is either true today or marked as not
yet true. Nothing here is a projection dressed as a fact.

---

## What it is

A comparison surface for the thirty seconds before someone opens a ride app.
It does not book rides, take a cut of a fare, or hold a rider's payment
details. It hands off to the provider's own app.

## What it shows today, honestly

RideLens currently runs on **one live source**: published regulatory rate
cards and tariffs, routed over OSRM, with a marketplace model on top for
time-of-day, demand and weather.

That produces a **modeled estimate**, and the product says so on every card —
a provenance chip on the price, a sheet that decomposes the number into the
rate-card lines it came from, and a `/sources` page that reports which sources
are actually running rather than which ones exist in the codebase.

**The product never implies it is showing a live in-app quote when it is
showing a model.** That is the design constraint the rest of the system is
built around, and it is the reason this document exists: a modeled estimate is
the honest floor, not the ceiling.

### What we do not do

- No scraping of any consumer app. Not Uber's, not Lyft's, not Obi's.
- No account credentials, and no acting on a rider's behalf inside a provider.
- No midpoint. A range is shown as a range, because collapsing it to one
  number is the most common way this category misleads people.

## Where a partner feed changes things

|                    | Modeled estimate (today)                       | Partner feed                                |
| ------------------ | ---------------------------------------------- | ------------------------------------------- |
| Basis              | Published tariff + routing + marketplace model | What the provider actually quotes           |
| Firmness           | `ESTIMATE_RANGE` with a stated band            | `UPFRONT_QUOTE` where the provider holds it |
| Surge              | Modeled from a deterministic simulation        | Real                                        |
| Account promotions | Not modeled, and stated as not modeled         | Reflected if the feed is account-scoped     |
| Accuracy           | Never measured against a real fare — see below | Measurable against the thing itself         |

The adapters already exist. Obi, Lyft, Curb, Empower and Uber each have a
written boundary in the codebase, ship dormant, and have a contract test suite
asserting that a dormant adapter **makes no network call at all** — no
endpoint is reached before authorisation is confirmed.

## What we will not do with your data

Stated plainly, because this is usually the concern:

- **Comparison rights are treated as a commercial question, not a config
  flag.** Uber's adapter refuses by default with
  `COMPETITIVE_COMPARISON_RESTRICTED` and cites the API terms, because the
  public Price Estimates API does not permit competitive comparison without
  written authorisation. It stays off until that exists.
- **A quote is labelled as what it is.** If a feed gives an estimate, it is
  not presented as a locked fare. Four quote types exist precisely so nobody
  has to round a promise up.
- **Coverage is not inferred.** A provider surfaces only in markets somebody
  verified. There are three coverage states — operates, does not operate, and
  _unverified_ — and unverified providers stay hidden. Empower is currently
  mapped to no markets at all for exactly this reason.
- **Caching honours the agreement.** Quote TTL is configurable and an adapter
  can opt out of caching entirely if the terms require it.
- **Credentials never appear in output.** There is a test for it.

## What we can offer back

Only two things, and both are real:

**Demand signal.** Every comparison is a rider with intent, at a known origin,
destination and moment, choosing between named options. What gets chosen over
what, at what price gap, is information a supply-side partner does not
otherwise see.

**Measured accuracy.** RideLens has an evaluation harness — `npm run eval`,
reported in `docs/CALIBRATION.md` — that scores predicted bands against real
fares on coverage, sharpness, bias and calibration, sliced by provider,
market, hour and distance. It refuses to report any statistic below 20
samples, and it refuses ground truth generated by the model itself.

**It currently has zero records.** The model has never been scored against a
real fare, and the calibration document says so in as many words rather than
publishing an encouraging number. A partner feed is the fastest path to that
document containing something.

## Current state, without varnish

|                                             |                                    |
| ------------------------------------------- | ---------------------------------- |
| Live sources                                | 1 — public rate cards + OSRM       |
| Dormant adapters                            | 5 — Obi, Lyft, Curb, Empower, Uber |
| Modeled markets                             | 49                                 |
| Markets with a modeled regulatory fee stack | 1 — New York                       |
| Measured accuracy                           | None yet; harness built and empty  |
| Riders                                      | Pre-launch                         |

The fee stack line matters and is easy to skim past: outside New York the
regulatory fees are **not** modeled, the product says so on the card, and the
band is widened to cover the gap rather than a plausible number being invented.
Chicago, Washington DC and Seattle are named in the code as needing someone to
read the actual tariff.

## What we are asking for

A conversation about a quote feed and the terms that would govern it. In
order of what would help most:

1. **Quotes for a defined market**, with the semantics stated — held or not,
   and for how long.
2. **Whether comparison display is permitted**, in writing.
3. **Attribution requirements**, so the surface is built right the first time.

If the answer is a licensed aggregator rather than a direct feed, that is a
good answer; the Obi path is already the primary one in the source matrix.

## How to check any of this

The repository is the argument. `docs/AUDIT.md` lists what was wrong and what
was fixed. `docs/QUOTE_SEMANTICS.md` is the contract for what a number means.
`docs/ENABLING_A_SOURCE.md` is the runbook a partner integration would follow.
`docs/CALIBRATION.md` is empty, and is supposed to be.
